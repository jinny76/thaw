> 配套文档:见 [PRD.md](./PRD.md)。本文档面向开发落地,细化会话生命周期、密钥派生、消息协议、富媒体传输与焚毁机制。
>
> 文档版本:v0.1 · 撰写日期:2026-08-26

---

## 0. 设计总纲(一句话)

服务器是一个**只认房间号、只转密文、不认识用户、不留任何东西**的哑中转;所有安全与状态都在浏览器端。**收发双方必须同时在线**,这是贯穿全局的硬约束。

关键决策(已在 PRD 定稿):
- **身份**:完全匿名,无登录/无注册。仅有会话内临时昵称(不落盘)。
- **密钥**:口令**带外**传递 + 房间号放 URL 路径;口令经 KDF 派生对称密钥,**口令与明文永不到服务器**。
- **富媒体**:图片/语音/文件,E2EE 分块经服务器内存实时中转,不落盘。
- **在线要求**:任一方离线 → 消息直接丢弃,服务器无暂存队列。
- **生命周期**:消息默认发送 5 分钟后自毁;退出聊天室 → 本端消息全销毁。

```
│  ├─ 内存消息表(易失)        │                              │  │   roomId → {A, B}    │
│  └─ 焚毁计时器             │                              │  └─ 帧转发(不解析明文) │

```

**技术栈**
- 前端:React + TypeScript + Vite;Web Crypto API;可选 Rust→WASM 做 Argon2id / XChaCha20。
- 后端:Node.js + `ws`(裸 WebSocket);无数据库、无 Redis、无持久化。
- 传输:全程 WSS(TLS)。

## 2. 会话生命周期

### 2.1 创建房间(A)
1. A 点「创建房间」→ **前端**生成 9 位随机房间号(避免服务器生成以减少可关联元数据;若担心碰撞,可让服务器在建立时校验唯一性并返回 `room_taken` 让前端重试)。
2. A 输入**进入口令**(自选,或前端生成一段高熵口令供 A 复制)。
3. 前端本地 `key = KDF(口令, salt=房间号)`(见 §3),密钥**只存在内存**。
4. A 向服务器发 `create_room{roomId}`(**不含口令、不含 key**)。服务器登记 `roomId → {A: conn}`,标记等待 B。
5. A 得到链接 `https://your-domain.example/123456789`,把**口令带外**发给 B。

### 2.2 受邀方进入(B)
1. B 打开链接 → 前端从路径取 `roomId`,向服务器 `join_room{roomId}`。
   - 若房间不存在/已满/已销毁 → 服务器回 `room_unavailable`,前端提示。
2. B 输入口令 → 走 **§3.1 的 ECDH + 口令认证握手**(交换临时公钥 → ECDH 派生会话密钥 → 用口令派生的 `authKey` 对双方公钥+roomId 做 HMAC 互相**常数时间比对**)。
   - 若 HMAC 不符(口令不一致,或服务器掉包公钥做 MITM)→ 握手失败、断开;**握手失败计入服务器限速计数(见 §2.5)**。
   - 服务器全程只见公钥与密文,不知口令、无法判断口令对错、换公钥必被 HMAC 发现。
3. 握手通过 → 双方各生成会话密钥 `sk` 与 `sessionToken`(仅内存)→ 进入聊天室,UI 显示「已连接 · 端到端加密」。

### 2.3 在线约束与断线
- 服务器维护 `roomId → {A, B}` 两个槽位。**只有两槽都在线才允许收发**;任一断开 → 服务器广播 `peer_left`,另一方 UI 转「等待对方…」,期间发送的消息被前端拒绝(不入队)。
- 若断开方在**短宽限期**(如 30s,可配)内**持原 `sessionToken`** 重连 → 恢复会话;超时 → 房间销毁。
  > **防房间劫持**:重连恢复**必须凭握手时生成的 `sessionToken`**(只存两端内存),而非"知道 roomId+口令就能接管"。这堵住了"攻击者在真用户断线瞬间抢占空槽"的劫持窗口。roomId 仅用于路由。
  > 注:宽限期是体验与「纯粹零状态」的折中。服务器在此期间仅保留「空槽位占位 + roomId + 待恢复 token 的哈希」这一最小元数据,**不保留任何消息**。

### 2.5 口令爆破防护:握手限速(必做)

> 因口令验证在客户端、服务器看不见口令对错,限速不能靠"服务器数口令错误",而要靠**服务器可观测的握手失败/加入频率**。分三层:

1. **在线限速(服务器强制)**:服务器对每个 `roomId` 统计握手失败次数——**每分钟 ≥5 次失败握手 → 立即销毁该 `roomId`**(而非锁定)。理由:合法用户几乎不会连错 5 次;一旦有人在猜口令,这个房间就已不可信,销毁最安全,创建者重建成本极低。同时对**单 IP** 跨房间的失败/join 频率限流,防房间号扫射。
2. **房间自然过期**:房间创建后 **N 分钟(如 10min)无人正确加入 → 自动销毁**,压缩在线爆破窗口。
3. **离线爆破由口令熵根治**:限速只挡在线爆破;攻击者截获密文后可在自己机器离线跑字典,服务器限不了——这部分靠 §3.4 高熵口令 + §3.1 ECDH(离线猜中 `authKey` 也无法回溯解密历史)兜底。

> 客户端握手失败时发一个**不含口令**的 `handshake_failed` 信号供服务器计数;即便恶意客户端不发,正常配对握手也绕不过服务器对 join/公钥交换频率的观测。

### 2.4 销毁(见 §5 详述)
- 任一方点「退出」或关闭页面 → 本端立即清空内存消息 + 密钥;通知服务器 `leave`。
- 服务器收到 `leave` / 检测到双方都断开且超宽限期 → 从内存 Map 删除该 `roomId`,会话彻底消失。

## 3. 密钥派生与加密方案

> ⚠️ **安全地基(必读)**:早期草稿曾设想「口令直接 KDF 出对称密钥 + 服务器转发密文握手」。**该方案不构成真正的 E2EE**——房间号公开(在 URL 里,服务器已知),口令是唯一秘密;服务器可对双方分别做 MITM 握手,并用口令字典离线爆破截获的密文。一旦猜中口令即可解密/篡改全部消息而双方无感。**本节据安全审计已改为 ECDH + 口令认证方案,这是 E2EE 成立的前提,非可选优化。**

### 3.1 握手:ECDH 密钥交换 + 口令短认证串(SAS)

**核心思想**:用 **X25519 ECDH** 建立会话密钥(保证前向保密、并使"服务器换公钥"这类 MITM 可被检测);口令**只用于认证信道**(证明对面是持口令的人、公钥没被掉包),**不直接充当加密密钥**。

流程(A、B 建立会话):
1. A、B 各自生成**临时** X25519 密钥对,经服务器交换公钥。
2. 双方各自算 ECDH 共享密钥 → HKDF 派生**会话密钥** `sk`。
3. **口令认证(防 MITM)**:双方本地 `authKey = Argon2id(口令, salt=SHA256("thaw:v1:"+roomId))`,各自计算 `tag = HMAC(authKey, A_pub ‖ B_pub ‖ roomId)`,经服务器交换并**常数时间比对**。
   - 若服务器掉包了任一方公钥做 MITM → 两端看到的 `A_pub‖B_pub` 不一致 → HMAC 对不上 → **握手失败、立即断开**。
   - 服务器不知道口令,伪造不出正确 `tag`;它换公钥必被发现。
4. 全部通过 → 进入聊天室,会话密钥 `sk` 只存两端内存。
5. **重连令牌**:握手成功时两端各生成并记住一个 `sessionToken`(随机、仅内存),用于 §2.3 断线重连恢复——**光有 roomId+口令无法接管会话,必须持 token**(堵住房间劫持)。

- **KDF 已落地 Argon2id(WASM)**:整条握手/加密/验证链路用浏览器原生 Web Crypto(X25519 ECDH、AES-256-GCM、HKDF、HMAC),唯一缺口 Argon2id 由 **`hash-wasm`**(预编译审计过的 WASM)提供,参数 `m=64MiB, t=3, p=1`,抗 GPU/ASIC 爆破。WASM 内联进 bundle(约 +45KB),无单独 `.wasm` 资源(顺带规避静态零缓存的重下问题)。若 WASM 加载/执行失败,`kdf.ts` 自动回退 `PBKDF2-HMAC-SHA256`(迭代 ≥600k)保证功能可用。接口 `deriveAuthKey(passphrase, roomId)` 不变,加密链路其余部分零改动。
- 有了 ECDH,即便口令较弱,离线爆破 `authKey` 也只能**冒充**发起一次在线握手,无法回溯解密已建立会话的历史消息(前向保密)。仍应配合 §3.4 高熵口令。

### 3.2 消息加密(对称)
- 用会话密钥 `sk` 加密:**AES-256-GCM**(Web Crypto 原生)或 **XChaCha20-Poly1305**(WASM)。
- 每条消息/每个文件块**独立 nonce**;AES-GCM 用**递增计数器 nonce**(避免随机 nonce 在同密钥下的碰撞风险),计数器只增不减。
- 关联数据(AAD)绑定 `roomId` + 消息类型 + `msgId`,防重放/串扰/跨房间重用。
- 富媒体每块单独 AEAD 加密并带 tag,接收端逐块校验(见 §6)。

### 3.3 前向保密与棘轮(M3 起支持,可迭代增强)
- ECDH 临时密钥 → 会话密钥天然带前向保密:会话结束、密钥丢弃后,即便口令泄露也无法回溯解密历史。
- 增强方向:按消息数/时间做**对称棘轮**(每 N 条 HKDF 推进一次 `sk`),缩小单个密钥泄露的影响面。非 MVP 必需,列为迭代项。

### 3.4 口令强度(根治离线爆破)
- **默认由前端生成高熵口令**:diceware 6 词 或 ≥20 字符随机串,用 `crypto.getRandomValues`。一键复制供带外发送。
- 允许自选口令,但对弱口令(短、纯数字、常见词)**强警告**并说明风险。
- roomId 同样用 `crypto.getRandomValues` 生成,**禁用 `Math.random()`**。

## 4. 消息协议(WebSocket 帧)

所有帧为 JSON;**凡含用户内容的字段一律是密文(base64)**,服务器不解析。

### 4.1 控制帧(服务器可读,不含内容)
| type | 方向 | 字段 | 说明 |
|------|------|------|------|
| `create_room` | C→S | `roomId` | 登记房间 |
| `join_room` | C→S | `roomId` | 加入房间 |
| `room_state` | S→C | `roomId`, `peers`(0/1/2) | 当前在线人数 |
| `peer_joined` / `peer_left` | S→C | — | 对端上/下线 |
| `room_unavailable` | S→C | `reason` | 不存在/已满/已毁 |
| `leave` | C→S | — | 主动退出 |

### 4.2 内容帧(服务器只转发密文)
| type | 字段 | 说明 |
|------|------|------|
| `ecdh_pub` | `pubKey` | §3.1 交换 X25519 临时公钥 |
| `auth_tag` | `tag` | §3.1 口令认证 HMAC,常数时间比对 |
| `handshake_failed` | — | 握手失败信号(不含口令),供服务器限速计数 |
| `msg` | `msgId`, `nonce`, `ciphertext`, `ttl`(默认 300s) | 文字消息 |
| `media_meta` | `msgId`, `kind`(image/audio/file), `nonce`, `ciphertext`(加密的文件名/大小/mime/总块数) | 富媒体元信息 |
| `media_chunk` | `msgId`, `seq`, `nonce`, `ciphertext` | 富媒体分块(见 §6) |
| `typing` | (可选) | 正在输入,不含内容 |
| `burn` | `msgId` | 通知对端提前焚毁某条(阅后即焚回执可选) |

> 服务器对内容帧的处理 = 「查 roomId → 找到对端 conn → 原样转发 → 不缓存」。看不懂也不需要看懂 `ciphertext`。

## 5. 焚毁机制(三层)

### 5.1 定时销毁(默认 5 分钟)
- 每条消息在**接收端渲染时**启动 `ttl`(默认 300s)倒计时;发送端对自己的消息同样计时。
- 到期:从内存消息表移除该条 + DOM 移除 + 触发「雪化」动效。
- 计时基准用**接收本地时间**,不依赖服务器时钟(服务器不参与)。
- UI 可显示每条消息剩余时间(小到毫无干扰的进度条/渐隐)。
- **边界(如实说明)**:TTL 焚毁**只对诚实客户端有效**。恶意/改装的对端客户端可无视 TTL 永久留存明文——这与"对方截屏"同类,是阅后即焚的**根本局限**,写入免责说明。

### 5.2 退出即焚
- 触发点:点「退出」按钮、`beforeunload` / `pagehide`、页面 `visibilitychange` 长时间隐藏(可选)。
- 动作:清空内存消息数组、置空密钥变量、断开 WS。
- **不写 localStorage / sessionStorage / IndexedDB**——从头到尾消息只在 JS 内存与 DOM。
- **边界**:`beforeunload` 不可靠(崩溃、断电、强杀进程都不触发),故它是"尽力而为"的清理;真正的保证来自"消息只在内存、进程结束即释放",不把 `beforeunload` 当安全承诺。

### 5.3 会话销毁
- 双方都离开 → 服务器删房间;任一方刷新且超宽限期 → 同上。
- 富媒体的 `ObjectURL` 需 `URL.revokeObjectURL` 释放,避免残留 blob。

### 5.4 恐慌热键:连按两次 ESC 关停一切

**热键**:**连按两次 ESC**(短时间内,如 800ms 窗口)。恐慌按钮应快,故不加二次确认。

**权限分级(关键):关服务器的能力,绑定在「已用口令进入聊天室」这一状态上。**
> 「访客可信」指的是**已用房间口令进入聊天室**的人可信;仅仅打开网站、还没进聊天室的访问者**不算**。因此:
> - **未进聊天室**(只打开首页,或打开链接但口令未输对/未完成握手)→ 连按两次 ESC **只关本地**(清屏、关标签),**无权关服务器**。
> - **已进聊天室**(通过 §2.2 密钥确认握手)→ 连按两次 ESC → 才能关服务器。

**动作链路:**
1. 连按两次 ESC → 前端本地立即销毁(清屏);若当前处于「已进聊天室」态,再向服务器发 `shutdown`。
2. 服务器:**仅接受来自已完成握手、处于活跃房间连接的 `shutdown` 帧**;校验通过 → 向**本房间**双方广播 `room_destroyed`(两端自毁清屏)→ 关闭这两个 WS → **`Map.delete(roomId)` 销毁该房间**。
3. 本端:清空内存消息 / 密钥 / Blob(`revokeObjectURL`)→ 跳空白页 → **`window.close()` 关闭浏览器标签**。

> **安全修正(重要):默认只销毁自己这个房间,不 `process.exit()`。**
> 早期设计让 `shutdown` 直接关停整个 Node 进程,但服务器是**多房间**的——那会让"任意一对进过房的人,掐断正在服务其他所有房间的进程",是可被滥用的 DoS。"访客可信"只在**单个封闭圈**内成立,不能跨房间成立。
> 故:**恐慌热键 = 销毁本房间**(对本圈子而言效果一样:会话没了、密钥没了、服务器该房间记录清空)。
> 若确实需要"关停整个进程"的全站总闸(仅限**你独占部署、只服务一个圈子**的场景):由服务器启动时读环境变量 `THAW_ALLOW_PROCESS_KILL=1` 显式开启,**默认关闭**;开启后 `shutdown` 才升级为 `process.exit(0)`。这样同一套代码在多租户下不会被误用。

**协议帧**:`shutdown`(C→S,服务器校验来源已入房)、`room_destroyed`(S→C 本房间广播,两端自毁并关标签)。

> **威胁模型前提(写入 README)**:进入聊天室需房间口令,故「能触发关停的人」=「持口令进过该房间的人」,在**该房间内**天然可信。跨房间无此信任,故默认收敛为只关本房间。

**浏览器限制(如实说明)**:`window.close()` 仅能关闭**脚本自己打开**的标签;用户手动打开的标签,JS 无法强制关闭,只能跳空白页并提示用户手动关。这是所有网站的通用安全限制,无法绕过。

### 焚毁的诚实边界(写入 UI 免责说明)
- 无法阻止对方**截屏、拍照、用另一设备录像**。
- 无法防御**端点被入侵**(键盘记录、内存取证)。
- 「已焚毁」只保证本产品自身不留档,不等于内容从物理世界消失。

### 5.5 反截屏:只能威慑与溯源,不能真正阻止(诚实结论)

> **Web 无法真正防截屏**——截屏发生在操作系统层(系统截图、手机组合键、另一台手机拍屏),网页 JS 在浏览器沙箱内够不到。任何"网页防截屏"都是有限障眼法。故本产品做的是**威慑 + 事后溯源 + 抬高成本**,并**如实告知用户不保证截不了**。

可落地的手段(效果如实标注):
- **失焦/切后台即糊**(有效中等):`visibilitychange`/`blur` → 消息区模糊遮罩,挡"切到截图工具/录屏切走"。契合间谍风,成本低。
- **隐写水印**(最实用):把接收方会话标识淡淡嵌入消息区背景 → 截屏了也能**溯源是谁泄的**。防不了截,但能追责。
- **可选「按住才显示」阅后即焚**(中等):敏感消息需手指按住才显现,松手即糊,抬高截屏操作难度。
- **PrintScreen 键监听 → 焚毁 + 通知对方**(弱/象征):仅桌面部分场景触发,Mac/手机无效,且截图已成。象征性威慑。
- ❌ **CSS 防截屏 / 网页 DRM 不存在**,不做虚假承诺。

> 定位红线:这些是"恶心成本 + 溯源",不是"密码学保证"。UI 与 README 必须写明。

## 6. 富媒体传输(图片 / 语音 / 文件)

**原则**:大文件不做单帧;端到端加密后**分块**流式经服务器内存转发,双方在线才可传。

流程(A 发文件给 B):
1. A 选文件 → 前端读为 `ArrayBuffer`,按固定块大小(如 64 KiB)切块。
2. 逐块加密 → 先发 `media_meta`(加密的文件名/mime/大小/总块数),再顺序发 `media_chunk{seq}`。
3. 服务器逐帧转发,不缓存、不重组。
4. B 收齐所有块 → 逐块解密 → 重组 `Blob` → 生成 `ObjectURL` 渲染(图片直接显示 / 语音用 `<audio>` / 文件给下载)。
5. 该富媒体消息同样受 5 分钟 TTL 与退出即焚约束;到期 `revokeObjectURL` 并丢弃 Blob。

**语音**:用 `MediaRecorder` 录制 → 得到 Blob → 走上述文件通道(kind=audio)。

**截屏直接贴图发送**:监听聊天输入框的 `paste` 事件,从 `clipboardData.items` 中取 `image/*` 类型 → 得到 Blob → 直接走图片通道(kind=image),无需先存盘。用户「截屏 → Ctrl+V」即可发送,体验对齐 WeChat/Slack。同理支持从文件管理器**拖拽**图片到聊天窗(`drop` 事件)。这两条都复用 §6 的分块加密流程,**服务器逻辑无需任何改动**。

**限制与健壮性(防对端打爆内存)**:
- **发送端**:设单文件上限(如 25 MiB,可配),超限拒绝。
- **接收端(不能只信发送端声明)**:在**重组缓冲层强制**同一上限——即便 `media_meta` 谎报大小/块数,累计接收超过上限**立即中止、丢弃已收块、销毁该消息**。校验 `seq` 连续、块总数不超过 meta 声明、并发接收的富媒体消息数设上限。
- **逐块 AEAD 校验**:每块单独 AES-GCM 解密验 tag,任一块 tag 失败即整条作废(防对端/中间人注入损坏块)。
**背压**:发送端按 `ws.bufferedAmount` 节流分块,防止塞爆。

## 7. 后端「零留痕」实现要点

- **无持久层**:不引入任何 DB / Redis / 文件写入。房间表是进程内 `Map`。
- **无业务日志**:不打印 roomId、内容、IP。仅保留崩溃级 `stderr`,且脱敏。
- **反向代理**(Nginx/Caddy):关闭 access log 或最小化;不记录 URL 路径(含 roomId)。
- **内存生命周期**:房间销毁即 `Map.delete`,让 GC 回收;不做任何快照。
- **无历史接口**:不提供任何「拉取历史」的 REST/WS 接口,从架构上杜绝。
- **元数据最小化**:服务器唯一掌握的是「某 roomId 此刻有几个连接」这一易失事实。

### 7.1 静态资源零缓存(本地不留任何文件)

**决策(已定):连应用静态资源本身(尤其 JS,以及 HTML/CSS/WASM)都强制不在浏览器落盘。** 每次进站/刷新都从服务器重新下载,关闭标签后本地不残留任何 app 文件。这是「本地不留痕」偏执威胁模型的选择——不仅会话内容不留,连"这台机器打开过雪泥"的代码指纹也尽量不留。

**服务端(nginx / 反向代理)** 对**所有**应用资源下发强不缓存头:
```nginx
location / {
    add_header Cache-Control "no-store, no-cache, must-revalidate, max-age=0" always;
    add_header Pragma "no-cache" always;
    add_header Expires "0" always;
    # 关闭访问日志,不记录 URL(含 roomId)
    access_log off;
    etag off;           # 不下发 ETag,避免协商缓存留痕
    if_modified_since off;
}
```
- `no-store` 是关键:它明确禁止浏览器写入任何缓存(内存缓存除外,内存随进程释放)。
- 关闭 `ETag` / `Last-Modified` 协商缓存,避免 304 复用磁盘副本。

**前端构建约束(nginx 管不到、必须靠代码保证):**
- **禁用 Service Worker / 不做 PWA**:Cache Storage API 绕过 HTTP 缓存头,一旦注册就会把资源持久化到磁盘。规范:项目**不引入** `vite-plugin-pwa` / `workbox` / 任何 SW 注册代码。
- **不用文件名 hash 长缓存策略**:Vite 默认给资源加 content-hash 是为了配合长缓存;本项目缓存已全关,hash 仅用于构建正确性,不改变 no-store 语义。可保留 hash(无害)或关掉。
- **单包体积控制**:因每次全量下载(含 WASM 加密模块),需**严控 bundle 体积**——按需加载、tree-shaking、WASM 尽量精简;把加载慢作为已知代价接受。首屏给「BOOTING SECURE CHANNEL…」的加载态(呼应 §8.5 风格),把下载时间转成体验的一部分。

**权衡诚实说明(写入 README):** 关闭静态缓存会让每次进站/刷新都重新下载整个应用(含 WASM),加载更慢、带宽更高。收益是本地磁盘不残留任何 app 文件。若后续觉得代价过高,可退化为「§7.1 备选:入口 no-store + hash 资源可缓存」——但**默认采用全量 no-store**。

## 8.5 UI / 视觉设计规范(暗网 · 间谍片风格)

**设计目标**:让界面本身传递「加密、隐秘、阅后即焚」的气质——像是间谍电影里那种加密终端 / 暗网聊天窗。冷、暗、克制、有科技感,但**保证可读性与易用性**(不为炫技牺牲聊天体验)。

### 视觉基调
- **暗色为底**:近黑背景(`#0a0e0d` / `#0d1117` 一类),避免纯黑,略带冷色调。
- **单色荧光强调色**:磷光绿(终端绿 `#00ff9c` / `#3bd671`)或冷青(`#00e5ff`)择一为主强调色,呼应老式 CRT 终端 / 黑客片。次强调可用琥珀色告警(焚毁倒计时、断线)。
- **等宽字体主导**:代码/终端感等宽字体(如 `JetBrains Mono` / `IBM Plex Mono` / `Fira Code`)用于时间戳、房间号、状态栏、系统提示;正文消息可用略易读的无衬线以保证长文可读。
- **扫描线 / 噪点**:极轻微的 CRT 扫描线叠加与颗粒噪点(低透明度),营造老终端质感——**默认可关**(无障碍/性能考虑)。
- **发光**:强调元素带轻微 `text-shadow` / `box-shadow` 辉光,克制使用。

### 关键界面
1. **落地 / 创建页**:居中终端窗口,像启动一个加密程序。打字机效果逐行输出:
   `> INITIALIZING SECURE CHANNEL...` `> ROOM ID: 123456789` `> AWAITING PEER...`。「创建房间 / 加入房间」两个入口做成命令行按钮风。
2. **加入 / 口令页**:输入口令框做成「解密」交互——输入正确后有「DECRYPTING… ACCESS GRANTED」的短过场动画。
3. **聊天窗**:
   - 顶部**状态栏**(等宽):`ROOM 123456789 · E2EE ACTIVE · PEER ONLINE · 2/2`,加密/在线状态用绿色常亮,断线转琥珀闪烁。
   - 消息气泡弱化圆角、偏「数据条」质感;己方/对方用左右 + 强调色区分。每条消息带**焚毁倒计时**(细进度条或角标 `04:59`)。
   - 系统消息(对方进入/离开、焚毁)用等宽 + `>` 前缀,像终端日志。
4. **焚毁「雪化」动效**:消息到期时不是简单消失,而是**逐字符溶解 / 像素崩解 / 绿色扫过后清空**的效果——把「阅后即焚」做成招牌视觉记忆点。这是产品的情感锚点,值得打磨。

### 动效与反馈
- 打字机文本、光标闪烁、消息发送时的「加密中…」微动效。
- 断线 / 对方离开:状态栏琥珀告警 + 轻微屏幕抖动或故障(glitch)一闪。
- 焚毁:见上「雪化」动效,配极短音效(可选,默认静音)。

### 技术落地
- 纯 CSS/Canvas 实现扫描线、辉光、溶解动效;避免重型库。
- 提供**「低调模式」开关**:关掉扫描线/噪点/辉光,退化为干净暗色终端,照顾长时间使用与无障碍。
- 严格遵守不留痕:主题偏好等**不写 localStorage**(或明确告知用户这是唯一的本地偏好且不含任何会话内容)。
- 移动端适配:等宽字体在小屏保证可读字号,状态栏可折叠。

> 设计红线:炫酷不能压过「看清消息、看清倒计时、知道加密/在线状态」。风格是外壳,聊天是内核。

## 8.6 工程规范(编码规范 · 测试 · CI)

> 定位:**这是一个正经的生产网站,不是 demo。** 编码规范与测试是一等公民,与功能同步交付,不事后补。

### 编码规范
- **语言**:前后端统一 **TypeScript**,开启 `strict`;禁用 `any`(必要处 `unknown` + 收窄)。
- **Lint / Format**:**ESLint**(typescript-eslint 推荐集)+ **Prettier**;规则冲突以 Prettier 为准。CI 上 `--max-warnings=0`。
- **提交规范**:**Conventional Commits**(`feat:` / `fix:` / `test:` / `docs:` …);配 **Husky + lint-staged** 在 pre-commit 跑 lint/format/typecheck,**pre-push 跑测试**。
- **命名与结构**:目录按 §8 分层;模块单一职责;纯函数优先(尤其 crypto/messages,便于单测)。
- **安全编码红线**:
  - crypto 层**不自造算法**,只封装成熟原语(Web Crypto / 审计过的 WASM 库)。
  - **严禁**把口令、明文、密钥写入日志、localStorage、URL query、错误上报。
  - **防 XSS(E2EE 的命门)**:一旦 XSS,攻击者能直接读内存里的明文与会话密钥,E2EE 全废。故:严格 **CSP**(禁 inline script、限制 connect-src 到自己的 WSS);消息内容**绝不 `innerHTML`/`dangerouslySetInnerHTML`**,一律作为文本节点渲染;富媒体只经 `Blob` + `ObjectURL` 渲染,不拼 HTML;链接渲染做白名单与转义。
  - **随机性**:所有密钥、roomId、口令、nonce、token 一律 `crypto.getRandomValues`,**禁用 `Math.random()`**。
  - **常数时间比对**:口令/HMAC/tag 校验用常数时间比较,防时序侧信道。
  - 依赖最小化;定期 `npm audit` / Dependabot;锁定 lockfile。

### 测试策略(测试金字塔)
| 层级 | 工具 | 覆盖对象 |
|------|------|---------|
| 单元测试 | **Vitest** | crypto(KDF/加解密/密钥确认)、消息 TTL 计时、富媒体分块/重组、房间状态机 |
| 组件测试 | **Vitest + Testing Library** | 聊天窗渲染、倒计时 UI、创建/加入交互、贴图/拖拽 |
| 集成测试 | **Vitest / Node** | WS 帧协议、房间配对、双端握手、断线/宽限期/重连 |
| E2E | **Playwright** | 两个浏览器上下文模拟 A/B:创建→带外口令→加入→收发文字/图片/语音/文件→5min 焚毁→退出全销 |

**特有的"零留痕"验证测试(不可省)——把承诺变成可执行断言:**
- **服务器不落盘**:集成测试中监控服务器进程工作目录/临时目录,断言一次完整会话后**无任何文件写入**(可用 fs 快照对比,或在测试沙箱用 `strace`/文件监视)。
- **无持久化 API**:断言服务器**不存在**任何拉取历史的接口(路由清单快照)。
- **前端零本地存储**:E2E 中断言会话全程 `localStorage`/`sessionStorage`/`IndexedDB` 为空(或仅含明示的非会话偏好)。
- **静态资源零缓存**:E2E 中断言所有应用资源响应头含 `Cache-Control: no-store`;断言**未注册任何 Service Worker**(`navigator.serviceWorker.getRegistrations()` 为空)、`caches.keys()` 为空。可选:检查浏览器磁盘缓存目录在会话后无新增 app 文件。
- **退出即焚**:E2E 中一方退出后,断言其页面内存消息表被清空、DOM 无残留、`ObjectURL` 已 revoke。
- **服务器只见密文**:集成测试中在服务器转发点抓取帧,断言内容帧 `ciphertext` 无法在无口令时解出明文(负向测试)。
- **加密正确性**:crypto 单测覆盖「同口令可解 / 错口令解不出 / 篡改密文 GCM 校验失败」。

**门槛**:crypto 与 session 核心模块**覆盖率 ≥ 90%**;整体行覆盖 ≥ 80%。覆盖率纳入 CI 门禁。

### CI / 质量门禁(GitHub Actions 建议)
`typecheck → lint → unit/integration(带覆盖率) → build → e2e(Playwright)`;任一失败阻断合并。
- PR 必须绿灯 + 至少一次评审才能合并。
- 依赖安全扫描(`npm audit` / CodeQL)纳入流水线。
- 主分支保护,禁止直接 push。

### 文档与可维护性
- 每个模块顶部注释职责;crypto/协议等关键决策沉淀到本文档(ADR 式)。
- README 含:本地起服务、跑测试、构建、部署、以及**诚实的安全边界说明**。

## 11. 威胁模型与已知边界(安全审计结论)

> 本节把"我们防什么、我们防不了什么"如实列清。诚实是本产品的信誉基础——**不做过度承诺**。

### 11.1 我们防御的(密码学保证)
- **服务器读取内容**:内容全程 E2EE,服务器只见密文与公钥。
- **服务器 MITM / 掉包公钥**:§3.1 的 ECDH + 口令 HMAC 认证会检测到公钥被换,握手失败。
- **口令在线爆破**:§2.5 握手限速(每 roomId 每分钟 5 次失败即销毁)+ 房间自然过期。
- **口令离线爆破**:§3.4 高熵口令 + §3.1 前向保密(离线猜中也无法回溯解密历史)。
- **消息篡改/重放/跨房间重用**:AEAD tag + AAD 绑定 roomId/msgId。
- **房间劫持**:§2.3 重连凭内存 `sessionToken`,非 roomId+口令。
- **服务器落盘/留档**:§7 零存储 + §8.6 自动化验证测试。
- **本地留痕**:内存-only、零本地存储、静态资源零缓存。

### 11.2 我们防不了的(如实告知,写入 README/UI)
1. **元数据(重点,勿低估)**:服务器/网络观察者天然可见——**双方 IP、连接与在线时间、消息收发的时刻与频率、每条密文的大小**。这些足以刻画"谁在何时跟谁聊了多久、聊了多少"。密文长度还会泄露消息类型与大致长度。
   - 缓解:消息**定长填充**到固定桶大小、掩盖 typing 频率;**IP 层需用户自行配合 Tor/VPN**——应用层解决不了。
2. **前端代码可信性(web E2EE 的根本局限)**:E2EE 依赖"浏览器跑的加密代码没被动过手脚"。服务器每次下发前端,**理论上可推送被后门的版本**。§7.1 的 no-store **不提升**此项安全(反而让"代码没变过"更难观察)。
   - 缓解:SRI 子资源完整性、发布构建产物哈希供第三方比对;将来可提供可选的桌面壳/浏览器扩展(代码固定、可审计)。**README 必须写明:你需要信任每次下发的前端代码。**
3. **端点安全**:对方**截屏/拍照/录像**、设备被入侵(键盘记录、内存取证)——密码学范围之外。
4. **焚毁靠客户端自觉**:TTL 与退出即焚**只对诚实客户端有效**,改装客户端可留存明文(见 §5.1)。
5. **恶意对端**:你聊天的对象本人可以保存、转发你发的内容——这是任何聊天工具都无法阻止的。

> **一句话免责**:雪泥保证"**平台自身看不见、不留档**",不保证"**内容从物理世界消失**"或"**对方一定诚实**"。安全由密码学 + 诚实的边界共同构成。
